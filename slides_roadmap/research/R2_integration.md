# R2 — Robot integration and the Pi–STM32H7 boundary

Research date: **2026-10-14**. Scope: a six-part research note, approximately six dense pages when typeset; no runtime, firmware, API or architecture changes. **PROPOSAL** denotes engineering recommendations requiring review, not an accepted interface or a demonstrated safety property. External sources were consulted on this date; vendor pages and repository default branches can change.

**Default path:** qualify power and the current camera, prove offline then live VIO and source-age performance, develop a small dedicated serial health interface, test rejection without actuation, then progress through stand → tether → supervised room driving → navigation. The Pi supplies optional perception/navigation input. STM32H7 retains body estimation, balance, LQR, VMC, FSM, motor limits and jump safety even when Linux disappears. This follows [ADR-001/002](../../docs/DECISIONS.md) and the [architecture](../../docs/ARCHITECTURE.md).

## 1. Evidence and the interface to review

The [13 October facts](../../experiments/2026-10-13-SESSION_FACTS_FOR_SLIDES.md) and [14 October addendum](../../experiments/2026-10-14-SESSION_FACTS_ADDENDUM.md) supersede historical inventory assumptions: the 8 GB Pi booted, but the 5 V/3 A supply still caused undervoltage; the 32 GB microSD constrained a moving stereo take; the 64 GB USB stick measured only 1.09 MB/s with fsync; a 15-second RAM recording was clean. The interrupted ORB rebuild and D435i replay/live validation remain OPEN. EuRoC accuracy establishes a known-input algorithm result, not robot readiness. NVMe and qualified bulk storage are not established by the draft [PROJECT_STATE](../../docs/PROJECT_STATE.md).

Current SDK serial is **317422076650**; USB/ASIC serial is **327743061057**. Keep SDK serial, ASIC serial, firmware-update ID and USB descriptor serial as separate manifest fields, even when values coincide; do not infer the current firmware-update ID from another serial. September calibration/qualification belongs to the old unit. Preserve the current IMU calibration warning and nominal/assumed configuration labels. See [calibration readiness](../../docs/D435I_VIO_CALIBRATION_READINESS.md) for historical provenance and the newer session facts for the active unit.

The [course deck, N5–N7](../../slides_course/main.tex) leaves wire format, rate, transport, covariance and stale budgets UNKNOWN. The following is a concrete **candidate for review**, not a public message definition. Start with health-only operation; enable navigation references only after N6 semantics and N7 safety approval.

| Direction / candidate record | Fields and interpretation |
|---|---|
| Pi → STM32 `PerceptionHealth` | Protocol version; message type/length; Pi boot/session ID; packet sequence; estimator sequence; estimator reset counter and map/frame epoch; tracking state (`STARTING`, `INITIALIZING`, `TRACKING`, `LOST`, `FAULT`); reason bitmask. |
| Freshness and validity in health | Pi monotonic send time; original estimate/source time and clock-domain ID; mapped estimate time plus mapping uncertainty when available; estimate age at send; flags for initialized, tracking, finite pose, finite velocity, frame/calibration accepted, clock mapping valid, resource fault and uncertainty available. No fresh estimate means no valid pose, even if heartbeats continue. |
| Optional Pi → STM32 navigation reference | Separate sequence and session, finite forward velocity in m/s and yaw rate in rad/s, body frame ID, source-estimate sequence/epoch, creation time and expiry/lease. Initially omit pose targets; later accept a target only with explicit reference/child frame, units, transform revision and reset semantics. Never send torque, balance gains or jump permission through this interface. |
| Optional Pi → STM32 observed pose/velocity | Position and quaternion of **robot body**, transformed from camera pose with reviewed extrinsics; velocity frame explicit. Local continuous `odom` and global `map` distinguished. Unsupported covariance is marked unavailable, never encoded as zero certainty or replaced with invented confidence. |
| STM32 → Pi status | MCU boot ID, sequence, MCU monotonic sample time/domain, FSM/armed state, operator enable, local balance/safety faults, battery status if measured, last accepted Pi/ref sequence, rejection reason, stale/fallback state and action time. Downsampled body attitude/rates, wheel encoder samples and leg configuration are optional diagnostics; timestamps identify sampling rather than transmission. |

The return path supports diagnosis and later reviewed wheel-odometry work; it does not authorize combining camera IMU and body IMU. If the camera is on the torso, leg-height changes move the torso relative to the wheel-ground frame: a fixed camera-to-torso transform must not be presented as a fixed camera-to-ground transform. Adopt reviewed SI/body/optical conventions from [REP-103](https://github.com/ros-infrastructure/rep/blob/master/rep-0103.rst) and continuous-versus-jumping frame semantics from [REP-105](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst).

**Candidate timing for synthetic/bench evaluation:** health **20 Hz**, status **20 Hz**, references at most **20 Hz**, sent only while valid. Publish estimate updates at their actual useful cadence; repeating a pose does not advance its source sequence or time. Candidate link silence timeout **150 ms**, maximum estimate age **150 ms**, and reference lease **100 ms**. These are proposed numbers, not measured Pi capability, manufacturer limits or approved safety budgets. Ratify or replace them before motor testing using N5 source-age tails, navigation speed/braking evidence and receiver timing. If throughput cannot meet the age bound, disable navigation and improve compute/input policy; do not silently lengthen the safety budget.

STM32 uses its local monotonic clock for silence/lease expiry and watchdogs. Four-timestamp exchanges can estimate a Pi↔MCU clock relation; record drift and conservative uncertainty, including path asymmetry. Also map device capture time into Pi monotonic time with evidence. Source age is evaluated at the **estimate epoch**, not the packet send time. A receiver computes an upper bound `A = MCU_now - mapped_estimate_epoch + mapping_uncertainty`; unknown mapping or excessive uncertainty invalidates optional navigation. A healthy link alone does not prove fresh perception. MCU timer wrap, Pi reboot and resynchronization require explicit tests. These are proposed methods grounded in the repo's [timestamp chain](../../docs/ARCHITECTURE.md), not an implemented synchronization service.

**Receiver policy:** validate framing/CRC/length/version/session/sequence, enums, finite values, frames, timestamps and required flags before updating accepted state. Bad packets never refresh the accepted-message timer. On absent/stale/invalid perception or reference, withdraw autonomous input and request a controller-owned, bounded ramp toward zero translational/yaw command; retain local balance feedback and motor protections. Simply disabling all wheel torque can topple a balancing robot. If the local controller detects a fall, battery hazard or motor fault, its existing safety FSM overrides the navigation ramp. Reboot/reset/map jump clears leases and requires session/frame re-establishment plus explicit operator re-enable; no automatic resumption after recovery. Stopping rate, fallback deadline and low-level loop-jitter bounds remain **UNKNOWN pending controller review**. Fail-safe authority is fixed; physical success is unmeasured [N7 deck](../../slides_course/main.tex).

## 2. Physical link and bounded packet handling

Repository inspection found [README](../../README.md) assigns **CAN to STM32 actuation/safety**; [native bring-up](../../docs/RPI5_NATIVE_PERCEPTION_BRINGUP.md) uses Ethernet/Wi-Fi for SSH control. Neither establishes a Pi–STM32 wire link. UART, USB-CDC, Ethernet and micro-ROS are candidates, not installed WBR facts. micro-ROS is middleware over a transport, not a connector: its [maintainer transport documentation](https://github.com/micro-ROS/micro-ROS.github.io/blob/master/_docs/tutorials/advanced/create_custom_transports/index.md) distinguishes framed streams from packet transports.

**Recommend a dedicated short 3.3 V UART at a candidate 460800 baud, 8N1**, with MCU DMA/bounded receive parsing and a low-priority mailbox consumed by the controller. Confirm available UART/pins, voltage, Linux console ownership and connector locking with the lab first. Raspberry Pi UARTs use 3.3 V, and Pi 5 routing differs from older boards ([official configuration](https://www.raspberrypi.com/documentation/computers/configuration.html)); do not copy a Diablo/older Pi pinout. Allocate fixed buffers; cap packet size and parser work; reception must never block the balance loop.

**Proposed framing:** zero-delimited COBS encoding of `version | type | payload_length | session_id | sequence | payload | CRC`, little-endian integers and explicitly specified float representation. Candidate CRC-32C parameters: polynomial `0x1EDC6F41` (reflected `0x82F63B78`), initial/final XOR `0xFFFFFFFF`, reflected input/output; cover all decoded header/payload bytes, excluding CRC and delimiter. Maximum decoded record **192 bytes**. Approve exact widths/layout and known-vector tests before implementation. CRC detects accidental corruption; it provides no authentication. Session negotiation prevents old-boot acceptance; modulo sequence comparison must have a bounded window and tested wrap. A sender keeps at most the latest unsent health/reference, with rejection/drop counters, and never retransmits an expired motion reference.

Calculated conservative budget: three 192-byte records per 50 ms interval across both directions, roughly 194 encoded bytes each, yields `194 × 3 × 20 × 10 = 116400 bit/s`, about **25%** of 460800 bit/s before scheduling overhead; UART is full duplex, so this aggregate is conservative. Serialization of one such record is about **4.2 ms**. These are arithmetic estimates, not measured latency. Check p99/max source age and MCU loop disturbance under motor EMI, Pi overload and burst traffic.

| Alternative | When it changes the recommendation |
|---|---|
| Dedicated CAN/CAN-FD | Switch if UART error/timing tests fail in the final harness and available transceivers, adapter, bus and isolation are confirmed. Keep perception off the motor bus unless worst-case arbitration/load is approved. Fragmentation, whole-message CRC, freshness and boot/sequence rules still need review. |
| USB-CDC | Use for a first receiver bench if the actual STM32 board already exposes it and UART access is unavailable; retain the same application envelope. Test unplug/re-enumeration, resets and back-power behavior; do not assume a debug USB port is a usable application link. |
| Ethernet/UDP | Use only if the board has confirmed MAC/PHY/interface and measured timing justifies it. Keep application integrity/session/age checks; reject late/out-of-order datagrams. The current Pi's loose Ethernet socket argues against making it the immediate default. |
| micro-ROS | Adopt if existing controller firmware already supports it and measured RAM, CPU and Agent failure behavior meet the boundary. Its [serial framing](https://github.com/micro-ROS/micro-ROS.github.io/blob/master/_docs/concepts/middleware/rosserial/index.md) includes CRC, but application freshness/authority still needs the same tests. ROS graph convenience alone does not justify adding it. |

## 3. Mechanical, electrical and emergency integration

**Proposed mount:** D435i forward-facing on the rigid torso, near its centerline and close to the body IMU when practical; avoid legs, wheels, moving head joints and long cantilever brackets. Select height/pitch by photographing the view at every allowed body pitch and leg height: include textured walls/furniture, avoid a floor-only view and wheel/leg occlusion. Record mounting drawings, mass, center-of-mass change and `T_body_camera` convention. Recheck controller payload/leg-height limits before balancing. Exact mount geometry and available bracket are **confirm with lab**.

PX4's [VIO guidance](https://docs.px4.io/main/en/computer_vision/visual_inertial_odometry) recommends soft camera mounting for vibration-sensitive airborne systems. **WBR inference:** begin with a stiff torso bracket, secure fasteners and short load paths, then measure vibration/blur with motors disabled and enabled. The D435i's camera and onboard IMU move together, but a soft camera-to-torso mount can introduce an unmodeled changing body extrinsic. If isolation is necessary, isolate the whole camera assembly in a restrained mount and measure compliance/resonance; do not hang the camera freely on foam or isolate a separately fused IMU differently. Improve wheel balance and structural resonances first. [Kalibr guidance](https://github.com/ethz-asl/kalibr/wiki/camera-imu-calibration) calls for good illumination, short exposures, all-axis excitation and avoiding shocks; it does not certify a WBR mount. Factory camera–IMU geometry is distinct from measured camera–robot geometry.

Use a short known-good USB3 data cable, strain relief at camera and Pi, slack across any relative motion, abrasion protection, and routing away from motor power wiring and wheel/leg pinch paths. Inspect full leg travel and potential fall contact. Confirm USB **≥5000M on the camera branch** with the final cable/topology. Changing mount/cable/hub/storage requires renewed relevant qualification; connector shape proves neither data speed nor current capacity [native bring-up](../../docs/RPI5_NATIVE_PERCEPTION_BRINGUP.md).

**Robot power proposal:** battery → separately fused/protected perception branch → appropriately rated DC-DC → **5.1 V/5 A at the Pi input**, with verified USB-C 5 V/5 A PD behavior and rated cable. Battery minimum/maximum voltage, regenerative spikes, converter thermal derating, fuse and connector ratings are **confirm with lab**, so no converter part is selected. Pi documentation recommends its 27 W supply; a detected 5 A supply permits a larger peripheral budget than a 3 A supply, and the USB/fan budget is shared ([hardware documentation](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html)). A converter's printed 5 A rating alone does not establish PD negotiation ([Pi USB-PD white paper](https://pip-assets.raspberrypi.com/categories/685-app-notes-guides-whitepapers/documents/RP-009856-WP-1-USB%20Power%20delivery%20on%20Raspberry%20Pi%205.pdf)). Do not force firmware current limits to hide an unqualified supply.

**Engineering proposal:** segregate motor/perception current returns, filter the perception branch, provide appropriate local decoupling and transient protection, and scope voltage at the Pi during worst approved motor load. Galvanic isolation is not assumed; use isolated power/data only if ground/EMI measurements justify it, with a complete electrical review. Avoid USB back-power paths. Provide active Pi cooling with unobstructed airflow; log temperature, clock and raw throttling flags during sustained combined acquisition/processing/link load. Protect the camera without covering apertures or trapping heat; consult the [D400 datasheet](https://realsenseai.com/wp-content/uploads/dlm_uploads/2025/08/Intel-RealSense-D400-Series-Datasheet-August-2025.pdf) for enclosure design limits. No jump/drop survivability is established.

Emergency actions remain local and independent of Pi/ROS/Wi-Fi. Confirm the lab's physical stop, remote stop, tether and recovery procedure. A stop that removes torque may cause a fall: protect people and equipment with the stand/tether and the controller's approved sequence. A Pi brownout must revoke navigation without resetting the STM32 through a shared power/data path. Storage finalization is secondary to immediate physical safety.

## 5. Robot test ladder, ground truth and failure mitigations

All stages below are **future proposed manual validation**, not execution authorization. No camera/ORB/sensor command may run before explicit **`CAMERA AVAILABLE`**. Preserve [lab runbook](../../experiments/2026-10-14-lab-prep/LAB_RUNBOOK_2026-10-15.md) N1 → N2 → N3: exact N2 **IR1 Y8 640×480/15, gyro/200, accel/100**, **20 → 105 → mandatory 300 seconds**, with unchanged timing thresholds. Stereo/30 development and a short RAM demo cannot substitute. Require calibration adequacy, offline/live VIO and N5 resource/source-age evidence before admitting robot navigation. N6 starts with synthetic semantics; N7 requires separate safety approval [course deck](../../slides_course/main.tex).

| Stage | Setup and measurement | Proposed exit / safety condition |
|---|---|---|
| 0. Synthetic receiver | No motors; scripted truncated/CRC-bad/oversize packets, duplicates, sequence/timer wrap, frozen estimate with fresh heartbeat, NaNs, wrong frame, reordered data, delayed queues, resets and reboot. | Every expected rejection/fallback transition recorded; no malformed record refreshes a lease; bounded parser work. Qualifies tooling/semantics only. Harness does not yet exist. |
| 1. Stand bench | Robot restrained, wheels off ground; health-only first. After authorization, bounded wheel tests. Measure supply transients, USB speed/errors, vibration, source age, UART errors and MCU loop period/jitter/overruns. Deliberately stop Pi/link/estimator. | No unexpected actuation or MCU reset; every injected fault revokes optional input inside approved budget; local control timing remains within reviewed limits. A stand cannot prove free balance or traction. |
| 2. Tethered balancing | Rated fall restraint that does not carry weight during nominal balance; clear area, operator at local stop; zero navigation then small authorized references. | Compare matched perception-enabled/disabled trials: pitch/rate, loop jitter, actuator saturation, fallback timing, tether loading and lost tracking. No fall/limit violation; Pi loss retains controller authority. Tether assistance invalidates a free-balance claim. |
| 3. Slow supervised room driving | Known flat route, manual commands, perception initially advisory, fixed initial view and surveyed checkpoints; clearance and measured speed/turn/acceleration limits. | Repeated tracking continuity, map/reset count, age tails, checkpoint/return error, stop distance and power/thermal logs satisfy predeclared budgets; failure produces local stop behavior. No autonomous obstacle-avoidance claim. |
| 4. Closed-loop navigation | Same bounded room; reviewed planner, obstacle input and command limiter; operator enable and local veto; repeated goals and deliberate stale/lost/reset events. | Goal/heading tolerance and clearance achieved across retained repeats, every fault handled safely, no silent resume/map jump. ORB localization alone is insufficient obstacle avoidance; any new depth stream/planner must be separately qualified and approved. |

Choose physical speed from measured stopping behavior: reserve clearance at least `v × (accepted source age + fault-detection/action delay) + measured braking distance + uncertainty margin`, plus robot footprint. This is a proposed conservative planning relation, not a certified safety calculation. The numerical speed, clearance, ramp and repeat-count budgets are **confirm with controller owner before tests**; lack of approved bounds blocks stage promotion.

**Without motion capture:** default to a tape-surveyed rectangular loop with measured checkpoint positions and heading marks, plus an independently fixed external camera if available. Report checkpoint and return-to-start position/yaw error, tracking losses and before/after-loop-closure results. Route length alone is not a time-resolved trajectory; endpoint agreement can conceal interior error or loop-closure correction. AprilTags with measured tag size, camera intrinsics and surveyed poses supply sparse reference observations ([AprilTag maintainer](https://github.com/AprilRobotics/apriltag), [pose interface](https://github.com/AprilRobotics/apriltag/blob/master/apriltag_pose.h)). Tags viewed by the same D435i share optical/calibration errors and may improve SLAM features, so label them an auxiliary reference, not independent motion capture. A calibrated fixed external camera observing robot markers can supply independent planar pose within its view; measure lens/ground-plane calibration, timestamp synchronization, tag-to-body offset and occlusion uncertainty. Do not report full 6-DoF ATE from unsynchronized endpoint or planar measurements.

| Moving-robot failure | Evidence to retain / proposed mitigation |
|---|---|
| Motion blur / fast pitch | Retain stereo pairs and exposure versus body angular rate; improve lighting, shorten exposure, cap turns/speed. D435i stereo uses global shutters, which still permit exposure blur ([D400 datasheet](https://realsenseai.com/wp-content/uploads/dlm_uploads/2025/08/Intel-RealSense-D400-Series-Datasheet-August-2025.pdf)); [Kalibr](https://github.com/ethz-asl/kalibr/wiki/camera-imu-calibration) recommends low shutter times and good illumination. |
| Vibration / mount flex | Correlate image blur and camera/body IMU spectra with motor speed; stiffen/secure mount, balance wheels, then test restrained isolation. Reassess body extrinsics after mount change; PX4 guidance is an analogy, not validation. |
| Wheel slip | Compare encoder prediction with body motion and visual/checkpoint evidence; cap acceleration and reject/downweight future wheel aiding during inconsistent/contact-lost periods. Keep wheel aiding deferred until frames/time/slip semantics are reviewed [course deck](../../slides_course/main.tex). |
| Featureless floors / repetitive texture / occlusion | Aim at textured static walls, inspect view over full pitch range, add surveyed landmarks where appropriate; cap motion and revoke navigation on LOST. Repeated corridors need checkpoint checks, not only a plausible map. These are WBR test hypotheses. |
| Darkness / glare / flicker / lighting changes | Retain representative images/exposure; qualify the room's lighting and shadows, limit exposure, test one condition at a time. Keep N4 emitter OFF baseline from [session facts](../../experiments/2026-10-13-SESSION_FACTS_FOR_SLIDES.md); adding depth/illumination is a separately qualified change. |
| IMU saturation during impacts/falls/jumps | Log unrounded raw vectors, clipping indicators/ranges when available, stamps and local fall events; exclude jumping from initial integration. Mark suspect intervals invalid and require reinitialization/operator enable after a fall. Do not copy old BMI055 range numbers onto current BMI085; active configured full-scale and survivability remain UNKNOWN. |
| Power/USB disconnect, CPU backlog, storage blocking | Preserve full kernel/power logs, queue age/drop counters and original timestamps; qualify DC-DC/cable/cooling/storage, bound unsent reference queues and revoke stale navigation. RAM-only short success does not qualify sustained storage [14 October addendum](../../experiments/2026-10-14-SESSION_FACTS_ADDENDUM.md). |
| Loop closure / reset / clock jump | Record map/reset epoch, transforms and source-time relation; use continuous local references, invalidate changed epochs and renegotiate. Never apply a discontinuous map correction directly as a balance state [REP-105](https://github.com/ros-infrastructure/rep/blob/master/rep-0105.rst). |
