# R1 — Algorithm and software path to WBR deployment

Research snapshot: **14 October 2026**. This is a recommendation for review, not an implemented architecture or gate receipt. **Default: retain ORB-SLAM3 stereo-inertial, qualify the existing native SDK path, then integrate ROS 2. Fallback: OpenVINS stereo VIO for local estimation if measured compute or recovery makes ORB unsuitable.** Neither is a balance controller. STM32H7 retains balance, LQR, VMC, FSM, motor and jump safety if the Pi fails ([project architecture](../../docs/ARCHITECTURE.md)).

Evidence labels: **MEASURED** means a cited repository observation; **SOURCE** means an upstream statement; **PROPOSED/INFERRED** means this roadmap's engineering judgment; **UNKNOWN** means not verified. External links were inspected for this research; mutable repositories must be pinned before implementation. Work for this ticket is documentation only: no SSH, installations, camera/ORB execution, upstream changes, or Git mutations.

**Decision:** ORB-SLAM3 is the right *next production candidate*, not a production-qualified estimator. Reuse the known build and input adapter instead of starting six ports. Qualify restart, Atlas save/load, initialization, tracking loss, map changes, resource tails and output validity before deployment. **PROPOSED switch trigger:** after stable power, correct calibration/timing and one-variable tuning, ORB repeatedly exceeds the §5 budget or fails representative rotation/recovery tests. Run OpenVINS on the **same retained inputs**, with the same evaluation/reference and compute measurements; switch only if it meets the approved operating envelope. If Jazzy PR/port cannot be reproduced, fallback remains unavailable. If both fail, stop navigation expansion and review motion envelope/compute placement rather than manufacture a pass. An OpenVINS switch gives up persistent global localization until a separately approved backend exists.

Common risk: a wheel-biped pitches, vibrates and may jump. Stereo-inertial helps metric scale and motion prediction, but no cited test qualifies these algorithms for this robot's impacts. First secure a rigid camera mount with cable strain relief, light/exposure control and measured vibration; an isolator that moves relative to the body requires modeling that motion. GPL-related deployment requirements need an owner decision; OpenVINS is not a permissive-licence escape. Basalt is a later evaluation candidate if that constraint becomes decisive, not a second immediate fallback.

## 2. ROS 2 path: qualify the native route before adding integration

**Existing choices:** [gjcliff's Jazzy wrapper](https://github.com/gjcliff/ORB_SLAM3_ROS2), used by this repository, advertises D435i Jazzy but supports **monocular and monocular-inertial only** and embeds a different ORB revision. [zang09](https://github.com/zang09/ORB_SLAM3_ROS2) exposes stereo-inertial, but its documented Ubuntu 20.04/Foxy setup is not Jazzy qualification. [Mechazo11](https://github.com/Mechazo11/ros2_orb_slam3) targets Humble and its published example is monocular; stereo is TODO. [suchetanrs](https://github.com/suchetanrs/ORB-SLAM3-ROS2-Docker) offers broader outputs/map services and odometry integration but targets Humble/22.04; a Jazzy simulation link does not qualify a Pi stereo-inertial container. A wrapper README is neither timing evidence nor a support commitment.

**PROPOSED shortest path:** once the native `stereo_inertial_realsense_D435i` record/replay route works, extract its acquisition/association logic into a small first-party C++ adapter, preserving checks and hashes. Add a thin `rclcpp` node linked to the **same qualified ORB library**. Keep acquisition, input association, estimator calls and ROS output conversion modular; do not shell out and scrape trajectory files. Implement only after node/API review. Initially SDK acquisition may own the device and publish diagnostics/outputs; the eventual N3 topic-input mode uses [realsense-ros](https://github.com/realsenseai/realsense-ros) as the **sole** camera owner. Prove equivalent native versus ROS inputs on replay before replacing the SDK source. No simultaneous SDK capture and live ROS camera process.

| Proposed input/output contract — names must match discovered graph | Content and checks |
|---|---|
| `/camera/infra1/image_rect_raw`, `/camera/infra2/image_rect_raw` and their `camera_info` | Lossless grayscale, paired capture epochs, actual profiles and optical frames. Rectify exactly once with matching intrinsics; never pair merely by subscriber arrival. Namespace is illustrative. |
| `/camera/gyro/sample`, `/camera/accel/sample`; optional derived `/camera/imu` | Preserve raw streams/IMUInfo/extrinsics. Interpolate accel only within valid brackets at gyro epochs; reject discontinuities, missing coverage and extrapolation. 200 Hz combined grid does not change 100 Hz raw accel information. |
| `/slam/pose`, `/slam/path`, `/slam/health` | Pose at source epoch, path for inspection, health with initialization/tracking state, reset/session/map identity, backlog, last valid source epoch and reason. Health message/API remains a proposal. |
| `/wheel/odom`, `/body/imu`, `/odometry/filtered` | Later robot integration; `nav_msgs/msg/Odometry`, `sensor_msgs/msg/Imu` and filtered local odometry. Do not invent covariance or relabel a camera pose as body pose. |

**TF ownership:** use REP conventions: `map` can correct globally; `odom` must remain locally continuous. For the robot, local wheel/body EKF owns **odom→base_link**. A validated SLAM bridge owns **map→odom**, computed at the *same epoch*: `T_map_odom = T_map_base × inverse(T_odom_base)`. URDF/robot-state publisher owns the mount chain and moving joints; camera driver owns internal camera transforms, without duplicate publishers. Optical axes are right/down/forward versus body forward/left/up. If the camera is on a moving link, its mount transform is dynamic. [Nav2 transformations](https://docs.nav2.org/rolling/configuration_and_development/first_time_robot_setup_guide/transformation/setup_transforms/), [filter frame semantics](https://raw.githubusercontent.com/cra-ros-pkg/robot_localization/ros2/doc/state_estimation_nodes.rst).

Audit the actual API: [ORB `TrackStereo`](https://github.com/UZ-SLAMLab/ORB_SLAM3/blob/master/include/System.h) returns camera-from-world pose; invert and compose the reviewed mount before publishing robot pose. Inertial trajectory export may use the camera IMU/body frame: it is not the robot body. Stock loop-corrected ORB poses must **not** masquerade as continuous local odometry. With no wheels yet, publish the diagnostic pose in an explicitly named SLAM world and defer Nav2; alternatively a separately qualified continuous VIO frontend can supply local odometry. Differencing a loop jump does not make it valid velocity. Reset invalidates alignment until re-established.

**QoS/recording:** inspect `ros2 topic info -v`. Use compatible sensor-data QoS (normally best effort, volatile, bounded queues) for images/IMU; size the IMU buffer to retain the image-bounded interval, count all losses and reject incomplete integration. Reliable subscription cannot match a best-effort publisher. Use reliable volatile state/health where compatible, and reliable transient-local `/tf_static`. These are choices to verify, not guarantees ([Jazzy QoS source](https://raw.githubusercontent.com/ros2/ros2_documentation/jazzy/source/Concepts/Intermediate/About-Quality-of-Service-Settings.rst)). N3 records explicit raw/calibration/TF topics locally to qualified storage; retain bag metadata, configuration and warning logs. Use reviewed [rosbag2 QoS overrides](https://raw.githubusercontent.com/ros2/ros2_documentation/jazzy/source/How-To-Guides/Overriding-QoS-Policies-For-Recording-And-Playback.rst). Stop live publishers, replay isolated, enable `/clock` and `use_sim_time` consistently, and reconcile every required stream's counts/stamps. The SDK's locally reported `.db3` extension alone does not prove standard ROS 2 message types or Kalibr compatibility; test readers and convert separately.

Nav2 needs timely continuous **odom TF plus odometry velocity**, global localization when using a map, sensor transforms, footprint, obstacle observations/costmaps and an appropriate planner/controller ([odometry guide](https://docs.nav2.org/rolling/configuration_and_development/first_time_robot_setup_guide/odom/setup_odom/)). ORB's sparse landmarks are not an occupancy map. Add qualified D435i depth and an occupancy backend such as RTAB-Map only in N5 after compute profiling; do not assume lidar. Standard planar Nav2 commands remain high-level requests to an STM32-owned locomotion/safety interface; they cannot command balancing torques or authorize jumping.

## 3. Wheels, body IMU and clocks

**When:** after N4 calibrated replay/live and N5 output evaluation, first record STM32 telemetry without fusion. Validate frames, time, encoder signs, scale and contact/slip on constrained ground motion. Then add loose coupling through `robot_localization`; upstream ORB's [sensor API](https://github.com/UZ-SLAMLab/ORB_SLAM3/blob/master/include/System.h) has image/one-IMU configurations, not a generic wheel or second-IMU input. Tight wheel factors would be a separate reviewed research change.

**PROPOSED STM32 publication contract:** acquisition-time ticks and tick units, boot/session ID, sequence and integrity checks; wheel encoder counts/velocities with scaling, sample interval and validity; leg/joint state needed for geometry; contact/airborne/slip flags; body gyro and optionally attitude/specific force with units, frame, saturation/calibration flags and uncertainty provenance. Publish derived wheel twist/odom on the Pi only when valid. Transport, update rate, covariance, age bound and receiver safety timeout are **UNKNOWN pending controller requirements**, not invented firmware fields. No firmware is changed by this report.

Start the local EKF with wheel forward velocity and justified body yaw-rate measurements. Do not fuse integrated encoder pose and velocity as independent observations from the same counts. On airborne/slip events withdraw wheel constraints; never enforce zero lateral velocity during jumps. Keep 3D body estimation; a planar navigation projection is a separate view, since `two_d_mode` constrains roll/pitch/height. Only add acceleration when orientation/gravity handling and impact behavior are verified. Sources: [filter configuration](https://raw.githubusercontent.com/cra-ros-pkg/robot_localization/ros2/doc/configuring_robot_localization.rst), [state-estimation parameters](https://raw.githubusercontent.com/cra-ros-pkg/robot_localization/ros2/doc/state_estimation_nodes.rst).

**Why separate IMUs:** different origins imply lever-arm acceleration, different axes/bias/temperature and independent clocks. VIO already consumes the camera IMU; feeding it again to an outer filter double-counts correlated information. Controller attitude may already include wheels or Pi feedback: audit lineage to prevent feedback loops. Camera IMU never replaces body IMU for balance. Later fusion requires rigid/dynamic extrinsics, calibrated clocks and justified measurement independence; even two separate IMUs are not automatically independent after estimator feedback ([project decisions](../../docs/DECISIONS.md), [Nav2 VIO integration guidance](https://docs.nav2.org/rolling/tutorials/general_tutorials/integrating_vio/integrating_vio/)).

**PROPOSED clock method:** STM32 stamps at encoder/IMU acquisition using a monotonic hardware timer; UART transmission/receive time is supplementary. Map unwrapped MCU ticks to Pi monotonic time using repeated bidirectional exchanges and an affine offset/drift fit, retaining round-trip delay and residual uncertainty. Timer/IRQ or DMA frame-boundary timestamps can reduce transport uncertainty; they do not recover unstamped acquisition time. Reject old sessions, wrap mistakes, duplicate epochs and out-of-order frames. Test injected delay/asymmetry before selecting a maximum source-age bound. Store device stamps, mapped stamps and mapping revision separately.

Use existing host synchronization or [chrony](https://chrony-project.org/doc/4.6/chrony.conf.html) for UTC logs; monotonic time measures processing. Do not step clocks during takes. PTP is optional only if the actual Ethernet/MCU hardware supports it; [linuxptp](https://www.linuxptp.org/documentation/ptp4l/) distinguishes hardware PHC and software timestamps. PTP/chrony does not synchronize a D435i hardware clock or an arbitrary UART MCU automatically. Independently characterize camera→Pi mapping and camera–IMU physical offset; same clock domain is necessary but insufficient. Hardware timer/UART/PTP support: **confirm with lab**.

## 4. Calibration toolchain and lab time

Use the active unit and final operating profiles/mount. Preserve **“IMU Calibration is not available”**, SDK logs and original calibration; do not write EEPROM/firmware. The September [readiness note](../../docs/D435I_VIO_CALIBRATION_READINESS.md) explains fallback provenance and transform checks, not calibration for this replacement camera. Older upstream [D435i documentation](https://github.com/realsenseai/librealsense/blob/master/doc/d435i.md) describes BMI055; this unit reports **BMI085**, so neither old noise constants nor that model label transfer.

1. **Camera intrinsics/stereo check first.** Confirm per-profile projection/distortion, rectification status, both image dimensions and baseline. Use a measured, flat [AprilGrid](https://github.com/ethz-asl/kalibr/wiki/calibration-targets); inspect coverage/corner residuals and stereo epipolar errors on held-out frames. **PROPOSED acquisition budget:** 2–3 minutes with varied view position/distance/angle, plus setup/review; not a manufacturer requirement. Calibrate raw images or the exact delivered rectified model consistently, avoiding double rectification.
2. **Prepare camera–IMU data, obtain noise before final solve.** Plan two independent **2–3 minute** all-axis motion takes (**PROPOSED**) with fixed target, good illumination, short exposure, rotations and translations; avoid shocks, planar-only motion, blur and saturation. The [Kalibr camera–IMU tutorial](https://github.com/ethz-asl/kalibr/wiki/camera-imu-calibration) requires noise parameters and calibrated IMU intrinsics or a model estimating them. Thus camera–IMU *capture* may precede Allan work; the final solve cannot skip its noise/intrinsic prerequisites.
3. **Allan deviation:** record full-precision stationary gyro/accel, preferably IMU-only, on a stable surface after temperature settles. [allan_variance_ros](https://github.com/ori-drs/allan_variance_ros) requests **at least 3 hours**; [Kalibr noise guidance](https://github.com/ethz-asl/kalibr/wiki/IMU-Noise-Model) recommends **15–24 hours**. Plan 3 hours for initial characterization and a longer scheduled run for bias-walk confidence; 60–100 seconds cannot qualify long-term walk. Fit supported averaging-time slopes, report uncertainty/temperature/gaps and units. Do not substitute rounded diagnostic CSV or blindly inflate noise by a generic factor.
4. **Solve spatial/temporal calibration offline**, preferably on the lab workstation (availability **confirm with lab**), using Kalibr's ROS 1 bag workflow in an isolated environment. Produce a derived bag from verified lossless images and raw/full-precision IMU with a reviewed interpolation path; preserve original timestamps/order, conversions and hashes ([bag format](https://github.com/ethz-asl/kalibr/wiki/Bag-format)). Use `kalibr_calibrate_imu_camera --bag derived.bag --cam camchain.yaml --imu imu.yaml --target aprilgrid.yaml`; temporal calibration is enabled by default. Review reports, residuals, plausible geometry and repeatability, not just optimizer exit status.
5. **Apply time offset once and validate held-out VIO.** Kalibr defines `t_imu = t_cam + timeshift_cam_imu` and `T_cam_imu` as IMU→camera ([YAML specification](https://github.com/ethz-asl/kalibr/wiki/yaml-formats)); ORB `T_b_c1` requires camera→camera-IMU, therefore invert. Test basis vectors/inverses, matrix layout and ms→s conversion. Keep a derived epoch for image/IMU association; do not rewrite raw stamps. Verify the pinned ORB parser's density/walk scaling rather than discretizing twice. Unknown offset, default geometry and assumed noise keep VIO qualification OPEN.

Durations are capture budgets, not guaranteed success; target detection and excitation determine usability. Three minutes of stereo/30 is **CALCULATED 3.32 GB image payload** before overhead, nearly the reported 3.9 GB RAM area; plan qualified external storage, not an untested longer RAM take. Allan IMU-only data avoids storing hours of images. **Confirm with lab:** measured AprilGrid/printing, controlled lighting and rigid fixture, adequate PSU/cooling, independently qualified dataset storage, workstation slot, and any reference trajectory system. None is assumed present.

## 5. Pi 5 performance and validation plan

**Baseline:** 8 GB Pi, Ubuntu 24.04/Jazzy, stable suitable supply and active cooling, headless ORB, no RViz on Pi, fixed release build/calibration, and no competing acquisition. [Pi power/cooling guidance](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html) recommends appropriate Pi 5 supply/cooling; retain power/throttle flags and actual frequency. A CPU `performance` governor is a **PROPOSED controlled experiment**, applied only in a later authorized session with before/after state recorded; no overclocking or persistent configuration here.

**Profile experiments after N2/N3:** qualify stereo **640×480 Y8/30** with emitter off, gyro/200 and accel/100, matching the prepared SDK program. If overloaded, compare stereo/15 at the same geometry; then a smaller *enumerated* native profile or documented software resize with adjusted calibration, one variable at a time. Lower FPS reduces compute but increases inter-frame motion. Do not alter N2's exact IR1/15 profile. **CALCULATED payloads:** stereo/30 = **18.432 MB/s**, stereo/15 = **9.216 MB/s**, excluding transport/serialization. Raw IR1 storage qualification is insufficient for stereo recording; qualify the final stream/storage arrangement. MicroSD remains OS/tools/small logs; RAM is a bounded diagnostic workaround, not durable storage.

**Threads:** capture callbacks enqueue bounded inputs; one association/tracking worker calls ORB in timestamp order; ORB local-mapping/loop workers remain asynchronous. Start with bounded OpenCV/BLAS parallelism, then measure before affinity changes. Leave CPU capacity for acquisition/ROS/health. Loop closure/map save stress belongs in profiling; disabling it changes behavior and cannot certify Atlas deployment. Pin binary/dependencies, dataset/settings and power/cooling before comparing runs ([ORB overview/thread architecture](https://github.com/UZ-SLAMLab/ORB_SLAM3)).

Measure **P50/P95/P99** separately for capture→pose age (only with a defensible clock mapping), callback→tracking wait, tracking-call duration and subscriber age. Record frame counts/gaps at device, driver, adapter, processed/rejected output stages; queue occupancy/slope; initialization, loss/reset/map timeline; CPU per process/thread, frequency, RSS, temperature, throttle/kernel/storage faults. Define CPU denominator (one core vs whole board). Retain raw event data and all trials; vocabulary/startup latency is separate from steady state.

**PROPOSED screening targets, to ratify before tests:** stereo/30 mean service time <33.3 ms, tracking P95 <33.3 ms/P99 <66.7 ms, mapped capture→published pose age P95 <100 ms/P99 <150 ms, stable bounded queues, zero unexplained capture/IMU loss, ≥25% whole-board CPU headroom, temperature <75°C and no power/thermal throttle. Stereo/15's period is 66.7 ms; retest the navigation age envelope rather than automatically doubling it. These derive from frame-period arithmetic and project headroom, **not published Pi guarantees or controller safety bounds**. Actual controller age budget is UNKNOWN. Existing N2 thresholds remain authoritative and unchanged.

The best project performance evidence is still under-voltage-confounded **282–301 s for 184 s of EuRoC**, including startup; no defensible P95/P99 exists ([N4A report](../../experiments/2026-10-13-n4a-euroc-mh01/REPORT.md)). Desktop sources in §1 justify profiling, not a 30 Hz promise. Repeat the stable-power EuRoC reference, then three calibrated D435i repeats, then **PROPOSED ≥30-minute** live tests including loop closure/map growth, representative rotations/vibration and simultaneous qualified recording. This later soak does not replace the mandatory 300-second N2 soak. Use ground truth when available for ATE/RPE; otherwise report continuity/recovery and reference-free drift checks without claiming accuracy.

**Future validation commands, not run here:** use the exact rebuild/linkage/native replay cards in the [lab runbook](../../experiments/2026-10-14-lab-prep/LAB_RUNBOOK_2026-10-15.md). After approval/authorization, build the proposed node with `colcon build --packages-select wbr_vio_bridge` (proposed package name), then `colcon test --packages-select wbr_vio_bridge` and `colcon test-result --verbose`. Offline/synthetic fixtures must cover stereo mismatch, IMU missing brackets/gaps/reversals, clock drift/wrap/reset, pose inversion, loop jump, stale output and recovery. N3 manual checks use `ros2 topic info -v TOPIC`, `ros2 bag info BAG` and isolated `ros2 bag play BAG --clock`, with complete count comparison. These checks prove tooling/integration only; no runnable bridge or new hardware PASS is claimed.

**Document validation:** 17 repository-relative links resolved; all seven comparison entries, five requested research areas and the final phase table were checked. Reproduce the local-link check from the repository root with `python3 -c 'from pathlib import Path; import re; p=Path("slides_roadmap/research/R1_algorithms.md"); links=re.findall(r"\]\(([^)]+)\)", p.read_text()); assert all((p.parent/u).exists() for u in links if not u.startswith("https://"))'`.
