# Supervisor bench demo

This is a bench demonstration of the perception-to-controller-message chain.
The drive command and filter are illustrative software; the Nucleo firmware
drives an emulated CAN motor endpoint. Keep the robot off the bench and treat
the filter as a demo policy, not a robot safety function.

## Before the supervisor arrives

On the Pi, connect the D435 recording setup, the Nucleo illustration board, and
the Pi-to-Nucleo serial link at `/dev/ttyAMA0`. Confirm the board is running the
AGV demo firmware and that its CAN2 endpoint is the fake motor. Do not use this
demo layout as evidence of a real robot or real motor response.

Run `tools/supervisor_demo/run_demo.sh [BAG_DIR]`. With no argument, the script
uses `~/wbr-evidence/lab-day-20261025/3-box13/camera-bag`. Foxglove connects to
`ws://<pi-address>:8765`; load `foxglove_demo_layout.json` for the camera,
advisory, filter state, fake wheel feedback, and IMU panels. Foxglove is optional
for launching and is skipped if `foxglove_bridge` is not installed.

## Five-minute walkthrough

Times are presentation cues; the bag is replayed at its recorded timeline and
the exact transition timestamps depend on the recording.

| Time | What the supervisor sees | What to explain |
| --- | --- | --- |
| 0:00–1:00 | The recorded color camera image plays. `/terrain_advisory` and `/safety_filter/state` update alongside it. | The Pi runs the obstacle node over recorded camera data. The command path is `/cmd_vel_teleop` → demo filter → `/cmd_vel`. |
| 1:00–2:00 | As the box enters the camera view, the advisory changes to `STOP_CANDIDATE`; the Nucleo board's advisory LED should turn red. | The stop rule applies when the candidate distance is at most 1.0 m. Forward command is clamped to zero; rotation is left as requested. |
| 2:00–3:00 | The `/cmd_vel.linear.x` trace drops to zero and the two fake wheel-speed traces fall toward zero. | The plot shows the filtered ROS command and firmware feedback from the fake CAN motor endpoint. This demonstrates message flow, not physical stopping distance. |
| 3:00–4:00 | When the box is absent from the recorded view, the advisory returns to `NONE`; the LED should return green and the fake wheel-speed traces rise again. | The demo filter passes the 0.3 m/s forward request under `NONE`. The command is generated by `drive_pattern.py`. |
| 4:00–5:00 | Show the advisory and IMU panels, then point out the complete flow on the boards. | The IMU is telemetry from the F446 demo firmware. Ask the supervisor to distinguish recorded perception from live sensing and simulated motor feedback. |

If the recording does not contain both clear-box and no-box sections, the
corresponding transition will not appear; do not imply a transition occurred.
The 300 ms advisory timeout is visible as `STALE` and clamps forward motion if
the advisory stream stops.

## What each board stands in for

- **Raspberry Pi 5:** the robot's perception computer, running ROS 2 Jazzy,
  recorded camera replay, obstacle advisory, and the demo command filter.
- **Nucleo-F446RE:** the planned robot STM32H7 control board. It receives the
  command and advisory topics and publishes feedback/telemetry using the AGV
  demo-board firmware.
- **CAN loopback and fake motor endpoint:** the RobStride motor interface and
  response path. Wheel feedback values are generated by the demo firmware, not
  measured from a real wheel or motor.
- **Recorded camera bag:** the D435 camera input in place of a live camera feed.

## What this does not prove yet

- Live camera capture, perception timing, and the Pi-to-controller path under
  the final robot's electrical, compute, and timing conditions.
- Correctness or completeness of obstacle classification for arbitrary scenes,
  terrain, lighting, camera movement, or box positions.
- A safety-rated stop function, safe stopping distance, braking behavior,
  watchdog behavior, or fault response on the robot.
- The STM32H7 implementation, real CAN bus behavior, RobStride response, wheel
  motion, or closed-loop robot dynamics. The F446 and fake motor endpoint are
  bench stand-ins.
- That `JUMP_CANDIDATE` should be traversed: the demo only limits forward speed
  and logs “would ask operator”; there is no operator approval interface.
- Validated behavior for `UNCERTAIN`; it passes through by this deliberately
  small demo policy unless the advisory stream goes stale.
