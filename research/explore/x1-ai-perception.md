# X1 — AI perception for locomotion and traversability

Research review, 2026-10-30. Scope: perception only; no training, camera/Pi access, motor commands or deployment performed. Hardware/data availability follows [BRIEF.md](BRIEF.md), which supersedes older worklog hardware descriptions. Sources below were opened; published results are not measurements on our rig. **UNVERIFIED** means a specific fact or artifact could not be established. This is a targeted landscape review, not a systematic novelty certification.

## 1. State of the art: nine relevant works

The useful progression is image labels → metric terrain geometry → persistent semantic/elevation maps → traversability conditioned on the robot. Image semantics alone cannot establish step height, load-bearing ability, friction or a feasible jump. A learned map can predict hidden terrain, but that prediction must remain distinguishable from an observed surface.

| Work, year, venue; opened paper/repository | Mechanism and relevance to WBR |
| --- | --- |
| Poudel et al., **Fast-SCNN: Fast Semantic Segmentation Network**, 2019, BMVC; [paper](https://arxiv.org/html/1902.04502v1), [author publication record](https://www.rudrapoudel.com/publications.html), [MMSegmentation implementation](https://github.com/open-mmlab/mmsegmentation/tree/main/configs/fastscnn) | Shared downsampling and a small convolutional network; **1.11M parameters** in the paper. A useful CPU baseline, rather than evidence of Pi real-time performance. The implementation is a reproduction, not an asserted author release. |
| Xie et al., **SegFormer: Simple and Efficient Design for Semantic Segmentation with Transformers**, 2021, NeurIPS; [paper](https://arxiv.org/abs/2105.15203), [official code](https://github.com/NVlabs/SegFormer) | Multiscale transformer plus lightweight decoder; B0 has **3.7M parameters** ([paper table](https://papers.neurips.cc/paper_files/paper/2021/file/64f1f27bf1b4ec22924fd0acb550c235-Paper.pdf)). Useful higher-capacity comparison; generic pretrained classes need adaptation to floor/step/obstacle scenes. |
| Wang et al., **RGB-D-Based Stair Detection and Estimation Using Deep Learning**, 2023, *Sensors* 23(4):2175; [journal metadata/abstract](https://pubmed.ncbi.nlm.nih.gov/36850775/), [author preprint with different title, 2022](https://arxiv.org/html/2212.01098v2) | StairNetV2 fuses RGB/depth features, detects stair lines, then estimates geometry. Preprint reports model files **10.4/2.87/0.95 MB** for 1×/0.5×/0.25× variants. Especially relevant to D435i; public runnable author code/checkpoints **UNVERIFIED**, so do not make the prototype depend on them. |
| Miki et al., **Elevation Mapping for Locomotion and Navigation using GPU**, 2022, IROS; [paper](https://arxiv.org/abs/2204.12876), [elevation_mapping_cupy](https://github.com/leggedrobotics/elevation_mapping_cupy) | GPU terrain fusion and local traversability processing, including a learned traversability filter. Strong mapping reference; CUDA/CuPy dependency prevents treating it as a drop-in Pi CPU package. |
| Ewen et al., **These Maps are Made for Walking: Real-Time Terrain Property Estimation for Mobile Robots**, 2022, IEEE RA-L; [SEL Map code and citation](https://github.com/roahmlab/sel_map), [project](https://roahmlab.github.io/sel_map/) | Bayesian fusion of RGB-D surface geometry and terrain-property distributions. Established precedent for semantic elevation maps; the project reports **5–25 Hz**, not a Pi 5 benchmark. Appearance-derived material properties remain estimates, not measured contact mechanics. |
| Erni et al., **MEM: Multi-Modal Elevation Mapping for Robotics and Learning**, 2023, IROS; [paper](https://arxiv.org/abs/2309.16818), [shared mapping code](https://github.com/leggedrobotics/elevation_mapping_cupy) | Fuses semantics, color and visual features into elevation-map layers. Direct precedent for projecting segmentation into our local map; that fusion itself is not a novel contribution. |
| Frey et al., **Fast Traversability Estimation for Wild Visual Navigation**, 2023, RSS; [proceedings](https://www.roboticsproceedings.org/rss19/p054.html), [WVN code](https://github.com/leggedrobotics/wild_visual_navigation) | Pretrained visual features plus online self-supervision from robot experience. The paper demonstrates rapid adaptation and outdoor navigation; our tabletop bags contain no equivalent locomotion outcomes. |
| Mattamala et al., **Wild Visual Navigation: Fast Traversability Learning via Pre-Trained Models and Online Self-Supervision**, 2025, *Autonomous Robots*; [journal](https://doi.org/10.1007/s10514-025-10202-x), [2024 preprint](https://arxiv.org/abs/2404.07110), [WVN code](https://github.com/leggedrobotics/wild_visual_navigation) | Extended self-supervised traversability system. Useful research comparator after the robot arrives; demonstrations on ANYmal/other platforms do not transfer the WBR's balance, wheel traction or clearance envelope. |
| **SemMap**, RAI Institute/ETH, repository accessed 2026; associated manuscript **Autonomous trail racing and parkour with a bicycle robot**, publication year/venue **UNVERIFIED**, under submission per [repository](https://github.com/rai-opensource/sem_map) | Current frontier implementation: frozen DINOv3 features, roughly **100k-parameter decoder**, semantic/traversability/confidence layers and ROS 2 mapping. Authors report about **90 Hz on AGX Orin**, not Orin Nano. Backbone is additional to decoder size. Research-only license, incomplete deployment/evaluation artifacts and AGX reference platform limit direct reuse. |

**Practical interpretation:** use learning for surface/obstacle recognition and ambiguity reduction; retain calibrated depth for dimensions. Neither a COCO object detector nor a Cityscapes road mask directly recognizes an indoor low step as safely traversable. Stair detection has task-specific precedent; negative obstacles need explicit observed-ground/visibility reasoning, not merely a missing-depth threshold.

## 2. What is visibly “wow” in a demo?

- **Terrain understanding display:** synchronized RGB overlay and a local overhead map showing floor, solid obstacle, step edge, stair sequence and unknown cells; attach measured height/distance and confidence. Move the camera around a box and show stable geometry despite changing viewpoint. A simple 2.5D grid is enough for the first demo.
- **A visible route choice:** show two passages, highlight a corridor with sufficient wheel/body clearance, and reject a blocked one. Before robot arrival, render the selected corridor and advice in replay; after arrival, moving through it requires separately validated navigation/control.
- **Recognize versus measure:** recognize “stairs” while drawing individual riser edges and their depth-derived dimensions. Show a deliberately ambiguous scene changing to UNCERTAIN rather than inventing a height. New staircase recordings are required.
- **Drop-off awareness:** show a supported floor ending at a measured edge, with unseen space behind it marked unknown. A depth hole from a shiny object should trigger uncertainty, not a fabricated gap. Do not use a real ledge traversal as the demo.

**Recommended first capability:** a semantic + geometric local terrain display with a passable-corridor proposal. It adds visible understanding beyond the existing NONE/JUMP/STOP/UNCERTAIN advice. Actual jumping/stair climbing is outside X1 and cannot follow from a perception label.

## 3. What is researchable or potentially novel for us?

**Candidate question:** does a small learned semantic model improve geometric hazard decisions under pitch motion, poor depth and compute contention, at the same observation-age budget on a wheel-biped?

The contribution would need to be a measured task benefit: fewer missed step/drop-off hazards or fewer unnecessary stops at matched hazardous false-pass rate. “Segmentation + depth + ROS” overlaps SEL/MEM; “online traversability learning” overlaps WVN; lightweight semantic fusion overlaps SemMap. Novelty remains **UNVERIFIED** until a focused comparison establishes a difference.

| Experiment | Comparison and claim boundary |
| --- | --- |
| Semantics versus geometry | Freeze the current depth detector; compare geometry only, RGB semantics only, and fused RGB-D. Evaluate identical recordings, confidence thresholds and hazard definitions. Semantic class confidence cannot override a positive geometric hazard. |
| Geometry conditioned on WBR configuration | Compare a fixed clearance/step rule against one using measured camera-to-body pose, leg configuration and wheel/body swept volume. Proposed added value is configuration-dependent decisions; mechanics limits remain unknown until measured. |
| Adaptive use of the neural model | Compare periodic segmentation with inference triggered by geometric ambiguity, at equal CPU/power or age budget. Measure decision quality and rejected/stale decisions, not just network FPS. This needs further scheduler/traversability prior-art review. |
| Later robot experience | After arrival and separately authorized controlled trials, learn traversability from actual passage/slip/controller outcomes. Split by physical scene and run; tabletop “looks passable” annotations cannot substitute for successful passage labels. |

Report event-level missed hazards, false passes, false stops, abstention/coverage, step-height and edge-distance error, class IoU, p50/p95/p99 observation-to-advice age, CPU/RAM and sustained power/temperature. Include uncertainty intervals over independent scenes/runs. Abstaining on everything must not win. Test unseen materials, lighting, viewpoints and pitch sequences; adjacent video frames must not cross train/test splits.

**Now:** Intel Mac CPU can run replay, annotation, reference inference and small decoder experiments; CPU inference on Pi is plausible at reduced resolution/low duty cycle, but candidate-specific sustained FPS with ORB-SLAM3 is **UNVERIFIED**. Start at 320×256 and target 2–5 semantic updates/s as an engineering goal, not a forecast. Quantify lost thin edges before downsampling further. Keep depth hazard processing independent of neural completion. No CUDA mapping package runs unchanged on either machine; implement a small CPU grid or postpone GPU mapping.

**Accelerator compatibility:** [Raspberry Pi AI HAT documentation](https://www.raspberrypi.com/documentation/accessories/ai-hat-plus.html) identifies AI HAT+ **13 TOPS = Hailo-8L**, **26 TOPS = Hailo-8**, both INT8. They accelerate supported inference, not SLAM, arbitrary point-cloud processing or online training. The same page now distinguishes AI HAT+ 2/Hailo-10H; its INT4 TOPS is not a substitute benchmark for this task. Official camera integration targets Raspberry Pi OS; our Ubuntu/Jazzy/RealSense path needs direct HailoRT integration. [Canonical's Ubuntu guide](https://ubuntu.com/blog/hackers-guide-to-the-raspberry-pi-ai-kit-on-ubuntu), **2024**, demonstrates feasibility but is not a current package-compatibility guarantee.

For custom Hailo models, use representative calibration images and a matching compiler/runtime/HEF target. [Ultralytics deployment docs](https://docs.ultralytics.com/integrations/hailo) require Linux x86_64 for compilation; our Intel Mac needs a suitable Linux environment or lab workstation. Coral likewise requires an Edge-TPU-compatible quantized export, not arbitrary PyTorch inference. Neither accelerator supplies a general CUDA environment for MEM/WVN.

**After arrival:** measure mounting extrinsics, camera visibility versus leg configuration, vibration/pitch, true wheel/body clearance, approach speeds and available power. Fuse depth using capture-time body attitude; BMI088 body IMU and D435i camera IMU have different frames/clocks. Sparse ORB landmarks are not a dense elevation map. A 2.5D grid cannot represent an overhang and ground in the same cell; retain raw-depth/body-clearance checks. Unknown depth is not traversable, and a positive semantic label cannot prove adequate traction. The MCU retains balance and motion authority; Pi outputs remain advisory.

## 5. What to request from the lab, and why

1. **First: continued D435i access, rigid mount, calibration target and measured terrain fixtures.** Boxes/ramps/short stairs, matte/dark/reflective surfaces and a guarded mock drop-off add more evaluation value than accelerator TOPS. Pi Camera v2 is useful for RGB recognition but provides no direct metric depth; substituting monocular learned depth requires a separate scale/error study.
2. **Borrow a Jetson Orin Nano Super 8 GB with cooling, storage and a suitable supply** for the broader learned-map direction. General CUDA/TensorRT support fits segmentation and CuPy exploration better than a fixed inference NPU; Nano memory/performance and ROS package ports still need measurement. [NVIDIA's official guide](https://docs.nvidia.com/jetson/orin-nano-devkit/user-guide/index.html) specifies up to **67 INT8 TOPS** and **7–25 W modes**; supply sizing must include camera, carrier, cooling and transients. AGX SemMap results do not promise Nano performance.
3. **Lower-cost Pi-preserving alternative: borrow AI HAT+ 13-TOPS Hailo-8L** to test one supported CNN and free CPU for SLAM. Request the 26-TOPS Hailo-8 only if measured model throughput/concurrency justifies it; no assumed 2× application gain. Check the Pi's PCIe/storage arrangement and cooling clearance before ordering. Choose Hailo when the target is a compiled perception model, Jetson when the target includes evolving GPU mapping/learning pipelines.
4. **Shared NVIDIA workstation time:** request an initial **8 GPU-hour allocation, 12–24 GB VRAM** for export/quantization and a small segmentation adaptation pilot. These are planning allowances, not published requirements or a training-time prediction; log the first run before expanding. Use the existing pretrained features initially rather than training a backbone from scratch.
5. **Coral only as an already-available loan** for a compatible small quantized model. The published dense-segmentation host sensitivity makes it a weaker first request than Hailo/Jetson for this scope. Measure total USB bandwidth/power alongside the RealSense rather than assuming an extra USB accelerator is free.

## 6. Two-week prototype using our rig/data

Plan only; this review did not inspect the archive or launch the prototype. Deliver replay first, then live perception when camera/Pi access is released. No motors or STM32 flashing. If new recordings/hardware are unavailable, retain the replay deliverable and explicitly leave stairs/gaps/accelerator results unverified.

| Days | Build/run and deliverable |
| --- | --- |
| 1–2 | Replay one 24 Oct bag through the existing depth detector; preserve its output as the frozen baseline. Read actual RGB/depth/calibration streams and timestamps. Render synchronized views, then add a small CPU local grid with observed/unknown flags. Confirm whether the scene even contains usable support-plane geometry. |
| 3–4 | Run one pretrained lightweight segmenter on extracted RGB, initially Fast-SCNN or supported MobileNet-based segmentation. Display its actual classes; do not relabel an unsupported “road” class as validated indoor floor. Annotate ~150 diverse frames for support/obstacle/unknown; split by scene/run, keeping a held-out recording. If only one scene exists, report within-scene feasibility only. |
| 5–6 | Fuse semantic probabilities with valid depth and camera calibration; estimate support plane, obstacle height, edge distance and corridor width. Preserve geometry vetoes and explicit uncertainty. If generic classes fail, try a frozen-feature small decoder; Mac CPU first, lab GPU if available. Run replay immediately and fix observed failures. |
| 7 | Produce a short replay demo with RGB labels, measured geometry, terrain grid and corridor proposal. Record failure cases. Existing boxes on a table cannot validate walkable-floor, stairs or gap detection; do not claim those results. |
| 8–9 | With released D435i, capture at least three independent sequences per scene condition: measured step/stair fixture, supported-floor edge/mock gap, reflective depth holes, clutter and handheld pitch. Record ruler dimensions and mounting/pose reference; reserve entire scenes/runs for final testing. No chassis motion is needed. |
| 10–11 | Run Pi CPU inference alone and concurrently with existing camera/SLAM. Sweep resolution and inference frequency; log capture-to-advice age in comparable clock domains, drops, RAM/CPU, temperature and power. If an accelerator is loaned, repeat the same replay/model where export permits; report model differences explicitly. |
| 12–13 | Evaluate geometry-only, semantics-only and fused arms on held-out runs. Include missing-depth/pitch/lighting cases and delayed semantic outputs. Publish false-pass/false-stop/coverage curves and geometry errors; report resource/age distributions and every failure. Small scene counts support a pilot, not a general safety claim. |
| 14 | Deliver a repeatable replay command/config, pinned model/export versions, annotated split manifest, failure gallery, comparison table and 60–90 s demo. Keep evidence outside git. Select the next experiment from measured benefit; if semantics adds no benefit at equal age/compute, preserve that negative result and defer hardware purchase. |

**Prototype success criteria (proposed, not results):** complete repeatable replay; a visible semantic terrain map and corridor overlay; no known geometric hazard cleared by semantics in the held-out pilot; fused-versus-baseline performance reported at matched false-pass rate with coverage; measured Pi age/compute under SLAM contention. A 5 Hz semantic stream with p95 capture-to-advice age ≤200 ms is an initial integration target, not a validated motion limit. Actual motion requires a separately established speed/braking/uncertainty envelope and owner-authorized robot work.
