# WBR AI capability roadmap

Prepared 2026-10-30 from the X1–X4 reviews, P1 brief, RL plan and scout synthesis. The robot path below is the **WBR**: Pi 5 over the actual WBR interface to the MCU; DM motors use DM CAN and there is no micro-ROS on this path. RobStride plus micro-ROS belong to the separate **AGV** path and are not assumed here. The STM32 remains responsible for balance and motor safety if the Pi, camera, network or learned software fails.

## Program 1 — “Go to the red box”: grounded, freshness-aware autonomy (WBR)

**Showable demo.** On a screen, the owner says “go to the red box.” The system labels the selected RGB-D object, shows its 3D location on the ORB-SLAM map, draws a route, and either reaches a safe goal in Nav2 simulation or refuses with a clear reason such as `STALE`, `UNKNOWN STEP`, or `RELOCALIZE`. First demonstration is replay/simulation on the 24 Oct tabletop bags; after lab access, run the perception portion live on Pi+D435i. Show target confidence, map/pose, path and capture-to-result age together. Do not imply that the saved box bags prove navigation or moving-person performance.

**Research question and measures.** Does an explicit age/uncertainty contract across object grounding, SLAM and planning reduce false or stale navigation goals under CPU/network delay while preserving useful target coverage? Compare a closed-set detector plus depth against an open-vocabulary or remote query on the same recorded frames. Measure target identity/3D localization accuracy against operator labels, false-goal and abstention rates, valid-goal coverage, capture-to-goal age (p50/p95/p99), stale-result rejection, map-reset/relocalization recovery, CPU/RAM, network bytes and end-to-end delay. Report replay and live results separately. This is an open research question, not a novelty claim. Relevant precedents include [VLMaps](https://arxiv.org/abs/2210.05714), [LM-Nav](https://proceedings.mlr.press/v205/shah23b.html), [ORB-SLAM3](https://doi.org/10.1109/TRO.2021.3075644), [Nav2 following](https://github.com/ros-navigation/docs.nav2.org/blob/rolling/docs/tutorials/general_tutorials/navigation2_dynamic_point_following/navigation2_dynamic_point_following.md), and the verified [information-freshness study](https://www.frontiersin.org/journals/robotics-and-ai/articles/10.3389/frobt.2026.1999591/abstract).

**Hardware and compute.** Start with the existing bags, Mac/Pi 5 (8 GB), and current ROS 2 + ORB-SLAM3 + depth-geometry stack. D435i is available only during lab visits. Request access to the existing edge-AI server/RTP path for offloaded open-vocabulary inference; the Pi remains responsible for pose, local geometry, freshness checks and refusal. Internet-cafe GPU PC access is limited to 2–4 h sessions with no admin: use those sessions for user-space model export/inference or short GPU trials, saving weights, logs and dependencies locally. P1 is measured (p1/RESULTS.md): YOLO11n 640 px is 22 FPS on the Mac but 3.4 FPS on the Pi 5 CPU with 4 threads, and it missed the books entirely. No accelerator is needed to start.

**Milestones.**

1. **This week:** run P1 against the saved bags when its user-space dependencies/model are available; save 5–10 overlays, detection/median-depth output and measured Mac pipeline FPS. Keep Pi FPS explicitly unmeasured until a lab session. Fix the COCO “box” class mismatch with a clearly labeled open-vocabulary or manually annotated comparison; do not treat `book` as `box`.
2. Freeze target labels, operator ground truth and score definitions; implement bag replay target grounding with capture stamps, frame IDs, confidence and abstention.
3. Feed timestamped targets to a Nav2 simulation and render map, target, route and status. Add delayed, reordered, repeated, missing and SLAM-reset responses; verify invalid/expired goals are rejected.
4. During a D435i lab visit, measure Pi camera-to-goal age/CPU/RAM under ORB-SLAM load. Compare local and RTP offload using the same frames and record bandwidth/queue policy.
5. If the repeatable demo works, add learned-feature relocalization proposals as an ORB-SLAM3 sidecar; compare relocalization success, tracked-frame fraction, false map changes and added latency against ORB-only. Keep ORB-SLAM3 as pose authority until evidence supports a change.

**Already done.** P1 reader, detector/export/benchmark scripts and honest run protocol are present in [p1/](p1/README.md); results are in p1/RESULTS.md (Pi 5 CPU 3.4 FPS; books missed). Existing project evidence includes Pi/D435i stereo capture and ORB-SLAM3 replay, depth-geometry obstacle advice, RTP/freshness coursework and saved box bags. These establish reusable components, not an end-to-end autonomy result.

**Main risk.** The 24 Oct bags are tabletop scenes, not a navigation sequence; COCO has no box or step class; current detector runtime dependencies and model are missing. A convincing recorded-data demo can therefore overstate capability unless ground truth, age and refusals are visible. Robot movement requires a separate authorized safety envelope; neither VLM output nor remote inference can command motors.

## Program 2 — See a step, negotiate it, keep balance: perception-aided locomotion (WBR)

**Showable demo.** The WBR rolls toward a measured low step, displays a local height/traversability patch and selected mode, slows, negotiates the step under a bounded controller and resumes rolling. Show a paired LQR/mode-switch baseline, body pitch/roll and failure/refusal traces. Begin with simulation and a restrained, low step only after robot commissioning and owner-approved physical trial conditions. No jumping is an initial milestone.

**Research question and measures.** Does a deployable, noisy and delayed depth-derived height patch improve low-step completion over the same proprioceptive baseline, and when does its age/uncertainty make it worse? Compare fixed LQR/mode switching, proprioceptive learning, and—only after model validation—a privileged-terrain teacher with a student that receives realistic D435i patches. Measure held-out step completion/falls, peak pitch/roll, time, energy/current proxy, step-height error, perception age/dropouts, fallback/refusal rate and inference/control timing. Use matched seeds and held-out conditions. Any learned output is bounded by the STM32 supervisor; the learned policy never replaces STM32 balance or safety.

**Hardware and compute.** Now: Mac for model inspection, existing planar MuJoCo only for balance/control questions it can represent, and Pi 5 for sensing/inference (not large-scale training). The current planar model cannot answer 3D step, five-bar contact or jump questions. After WBR arrival, obtain CAD/masses/inertias, linkage geometry, motor torque-speed/current/thermal limits, encoder/IMU timing and CAN schedule before making a 3D model. D435i remains lab-visit-only. Use internet-cafe GPU PC in 2–4 h, no-admin sessions only if a user-space toolchain and GPU are confirmed at session start; persist and export all artifacts. RL plan sets a 12 GPU-h cafe ceiling and does not authorize paid Isaac migration. Hailo is for supported inference, not MuJoCo/PPO training.

**Milestones.**

1. **This week:** freeze a low-step task specification, success/failure thresholds, matched LQR baseline and required post-arrival measurements; inventory a no-admin GPU-PC session with a tiny user-space throughput/checkpoint-reload smoke test only if access is available. No tuning of stopped PPO or owner-only gain schedule.
2. After arrival, validate CAD/URDF-to-MuJoCo geometry, static balance, joint signs/ranges, wheel contact, actuator limits and timing against measured hardware. Stop at a parameterized model if inputs are missing.
3. Validate baseline flat-floor tracking and low-step simulation across held-out heights, speed, friction, payload and sensor delay; preserve all failures and compare with unchanged LQR/mode-switch logic.
4. Add teacher/student height-map input and realistic depth holes, occlusion, delay and CPU-rate constraints. Evaluate multiple seeds and an untouched test panel; do not claim transfer from simulation.
5. Only after commissioning and an approved, restrained trial, run a small physical comparison with the STM32 enforcing balance, torque and stale-map fallback. Progress beyond low steps requires a new evidence review.

**Already done.** A planar MuJoCo model and historical PPO v1/v2/v3 evidence exist; v2 underperformed its frozen LQR reference and v3 failed its frozen screens and is stopped. There is no validated 3D WBR model, no measured WBR motor/dynamics envelope and no robot yet. The applicable precedents are not transferable guarantees: [wheeled-legged RL/navigation](https://arxiv.org/abs/2405.01792), [perceptive locomotion](https://doi.org/10.1126/scirobotics.abk2822), [RGB-D terrain-to-mode selection](https://scholars.lib.ntu.edu.tw/entities/publication/e2ca58bb-ee17-4d98-89d7-9fca9f59efd0).

**Main risk.** Model error at the five-bar linkage, contact and motor limits can make simulation reward meaningless or unsafe. Cafe availability may not provide the needed GPU/runtime, and 2–4 h sessions limit debugging continuity. Hardware trials remain gated on commissioning and verified STM32 fallback. The existing weak PPO result is not a basis for a physical learned controller.

## Recommendation

Start Program 1 this week: it has real D435i recordings, a working P1 code path, the most immediate visible result and a useful research question that can be tested before robot delivery. Keep the first demonstration replay-based and show measured age, failures and abstentions; then add live Pi and navigation simulation when access permits. Program 2 should proceed through model/data preparation but wait for the robot’s measured geometry and actuator envelope before training or physical trials. **X1 must answer the purchase question with an end-to-end comparison on our Ubuntu/ROS 2 + D435i workload:** does Hailo-8L on AI HAT+ materially improve task accuracy/coverage and p95 camera-to-map latency under concurrent ORB-SLAM3, compared with Pi CPU and the existing edge server, after including host preprocessing and conversion effort? If the intended task is local open-vocabulary/VLM autonomy, compare AI HAT+ 2 or a borrowed Orin Nano Super separately; TOPS alone is not an answer. Do not buy an accelerator until those measurements identify a real bottleneck and compatible model path.
