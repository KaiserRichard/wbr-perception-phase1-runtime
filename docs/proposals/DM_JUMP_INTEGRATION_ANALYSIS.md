# TerrainAdvisory Integration Analysis

Source reviewed: github.com/nguyenbinh-shark/DM-jump at commit 6855ef8 (read-only clone, 25 Oct 2026). Written by codex-e; Claude 2 spot-checked the PS2 jump trigger and USART1 settings.
Read-only review of the DM-jump STM32H723 CubeMX/Keil source and the proposal/link bench material. This is an owner-review note, not an approved interface or firmware change. `TerrainAdvisory` remains advisory only.

## 1. Existing architecture and jump path

- **RTOS:** FreeRTOS through CMSIS-RTOS v1. Six CubeMX tasks plus UART parsing and UART-control tasks are created in `Core/Src/freertos.c:112-149`.
- **Task rates / priorities:** priorities below are CMSIS names (relative ordering); stack-size parameters are declared in `Core/Src/freertos.c:112-149`.

  | Task | Priority | Observed cadence/work |
  |---|---|---|
  | `INS_TASK` | Realtime | `osDelay(1)`; nominal 1 kHz INS/attitude update (`User/APP/INS_task.c:58-62, 155-175`). |
  | `CHASSISR_TASK`, `CHASSISL_TASK` | AboveNormal | Continuous loop; one balance computation then three separate `osDelay(1)` calls while sending three motor frames. Thus roughly 333 control passes/s before computation/scheduler overhead, not a measured hard rate (`User/APP/chassisR_task.c:71-95`; `User/APP/chassisL_task.c:52-78`). |
  | `OBSERVE_TASK` | High | `OBSERVE_TIME=3 ms`, nominal 333 Hz (`User/APP/observe_task.c:47-56, 70-97`). |
  | `PS2_TASK` | AboveNormal | `PS2_TIME=10 ms`, 100 Hz poll (`User/APP/ps2_task.c:48-69`). |
  | `UART_TASK` | AboveNormal | Blocks waiting for one-byte RX queue; parses complete ASCII lines (`User/APP/app_uart.c:68-90`). |
  | `UART_CONTROL_TASK` | Normal | 10 ms delay, but current function body only delays; it does not forward parsed commands (`User/APP/uart_control_task.c:17-22, 40-47`). |
  | `defaultTask` | Normal | 1 ms delay (`Core/Src/freertos.c:160-168`). |

- **Balance/control:** each chassis task calls its side's `*_control_loop`; LQR wheel/leg feedback and the VMC calculation are in `User/APP/chassisR_task.c:180-218` and `User/APP/chassisL_task.c:130-194`. Five-bar/VMC mapping is called through `VMC_calc_2` in the latter; LQR gains are interpolated per leg. INS is separate.
- **Jump FSM/sequence:** coordinated per-side `jump_loop_r`/`jump_loop_l` live in the chassis control source, not a separate central FSM (`User/APP/chassisR_task.c:267-337`; `User/APP/chassisL_task.c:197-241`). Crouch (target 0.08 m), thrust (0.21 m), retract/landing, then reset; right-side code synchronizes side status transitions and clears `jump_flag` after both sides reach status 3.
- **Current trigger:** PS2 key value 12 (commented R1) held for more than 10 polls sets `jump_flag` and captures leg height (`User/APP/ps2_task.c:303-323`); at 100 Hz that is roughly 100 ms of hold. USART1 ASCII `J` is parsed into `uart_cmd.jump_trigger` (`User/APP/app_uart.c:168-170`), but the present UART-control task is a delay-only stub. No connection from that field to `chassis_move.jump_flag` was found. Therefore PS2 is the only active jump trigger evidenced by this code review.

## 2. Peripherals and Pi UART feasibility

- **Configured UART inventory:** `CtrlBoard-H7_IMU.ioc:103-115, 423-424` lists USART1 as the only UART/USART peripheral configured. No UART DMA request/stream appears in the IOC DMA entries (`CtrlBoard-H7_IMU.ioc:8-42`). USART1 is 115200, 8N1, TX/RX, no flow control, oversampling 16, prescaler DIV1 (`Core/Src/usart.c:47-58`). MSP selects D2PCLK2, maps PA9 TX / PA10 RX as AF7, and enables USART1 IRQ at NVIC priority 5 (`Core/Src/usart.c:91-117`). It currently carries host ASCII command/telemetry traffic; RX is interrupt-per-byte into a 64-byte FreeRTOS queue (`Core/Src/usart.c:151-166`; `Core/Src/freertos.c:107-110`; `User/APP/app_uart.c:17-23, 74-90`).
- **Other UARTs:** USART2/3, UART4/5, USART6/7/8 and LPUART1 are not configured or initialized in the IOC/source inspected. No configured free UART pin pair is evidenced. USART1 PA9/PA10 are physically configured but occupied by the existing command/telemetry channel. A replacement or multiplexing decision is needed before using it for Pi advisory traffic. Any alternate free UART instance and board-routed pin pair are **UNKNOWN**: no board schematic/net map was present. Do not infer that an MCU alternate-function pin is exposed on a connector.
- **460800 arithmetic:** the project clock tree is HSE 24 MHz, PLL1 SYSCLK 480 MHz, HCLK 240 MHz, APB2 120 MHz (`Core/Src/main.c:179-213`; `CtrlBoard-H7_IMU.ioc:315-355, 382-388`). USART1 selects D2PCLK2; the configured APB2 clock is 120 MHz. At DIV1/16x oversampling, ideal BRR is 120,000,000 / 460,800 = 260.4167; nearest integer divisor 260 gives 461,538.46 baud, about **+0.1606%** error. This is calculated from source clock settings, not measured on the board. Actual clock tolerance, signal integrity, and Pi-side matching remain to be measured. The 460800 setting is technically achievable without a clock-tree change if this clock configuration is active.
- **FDCAN / motors:** FDCAN1 is on PD0 RX / PD1 TX and uses nominal prescaler 4, segments 1+19+5, 100 MHz kernel clock = 1 Mbps; chassis right motor traffic uses it (`Core/Src/fdcan.c:42-73, 193-207`; `User/APP/chassisR_task.c:76-94`). FDCAN2 is PB5 RX / PB6 TX, prescaler 5, segments 1+14+5, same 100 MHz clock = 1 Mbps; chassis left uses it (`Core/Src/fdcan.c:90-124, 223-237`; `User/APP/chassisL_task.c:57-75`). FDCAN1/2 are started/configured in application code (`Core/Src/main.c:133-135`). FDCAN3 is initialized on PD12/PD13 and uses matching nominal timing, but no motor use/start was found (`Core/Src/fdcan.c:127-174, 242-278`; `CtrlBoard-H7_IMU.ioc:251-254`). These are FDCAN peripherals carrying classic CAN frames, not UART options.

## 3. Receive-only parser placement and resource envelope

- Receive into a bounded UART DMA circular/ring buffer (or DMA idle-line chunks feeding a bounded ring); ISR/callback work should only publish byte positions/events. Decode outside interrupt context in a new low-priority task. Use the proposed COBS delimiter framing and CRC-32C from `tools/link_proto/SPEC.md:19-47`; validate exact version/type/length and advisory fields before publishing. The proposal's TerrainAdvisory is type 4, 42-byte payload; header+payload+CRC is 62 decoded bytes and up to 64 bytes on wire (`TERRAIN_ADVISORY_FIRMWARE_PROPOSAL.md:20-49`; `tools/link_proto/SPEC.md:140-148`).
- Expose a read-only, atomically copied snapshot such as `{advisory, distance_m, height_m, age_ms, fresh}`. Timestamp acceptance with the MCU's local monotonic tick; do not subtract Pi monotonic or camera timestamps from MCU time. After 300 ms without an accepted message, report stale and make the advisory unusable, per proposed policy (`TERRAIN_ADVISORY_FIRMWARE_PROPOSAL.md:104-117`). Invalid/duplicate/stale packets must not refresh age. No parser path should alter balance state, outputs, or block a control task.
- **F446 reference only:** proposal reports the whole F446 bench image (codec + app + LED support) at 7,568 B text, 5,120 B BSS, 12,688 B combined; it is not an isolated parser measurement and cannot be used as an H7 budget (`TERRAIN_ADVISORY_FIRMWARE_PROPOSAL.md:119-125`). Bench observations include 15 Hz records and 900/900 echoes; they do not report MCU parser cycle count (`TERRAIN_ADVISORY_FIRMWARE_PROPOSAL.md:45-49, 64-79`). H7 CPU cost and exact flash/RAM delta are **UNKNOWN** until built/measured by the owner. As a planning estimate only, 2×64-byte RX buffers plus one 62-byte decoded buffer and one ~48-byte advisory snapshot would be about 238 bytes of raw storage, before metadata, alignment, task stack, or counters. This is a design estimate, not an F446 measurement or H7 guarantee. At 15 Hz the maximum 64-byte frame is about 9.6 kbit/s (proposal calculation), low link utilization, but scheduling must still be measured.

## 4. Future FSM consumption boundary (owner proposal)

Keep the first integration telemetry-only. If later approved, the local FSM could consider a jump only when **the operator requests jump AND** a locally accepted advisory is fresh, equals `JUMP_CANDIDATE`, and its distance is inside an owner-defined window. Firmware must still require its own supported/armed state, balance/contact/clearance and actuator checks, local jump mode, and safety vetoes. Stale, invalid, `NONE`, `STOP_CANDIDATE`, or `UNCERTAIN` must never initiate motion; the Pi has no jump, torque, enable, or veto authority. The proposal explicitly reserves all transitions and safety decisions to STM32 (`TERRAIN_ADVISORY_FIRMWARE_PROPOSAL.md:8-13, 115-117`). Distance window and relevant local conditions are **UNKNOWN / owner decisions**.

## 5. Risks and unresolved points

- Chassis control cadence and worst-case jitter are not measured; nominal three 1 ms transmit delays imply ~333 Hz passes, while the LQR/VMC time-step argument is 3 ms (`User/APP/chassisR_task.c:55, 71-85, 180-183`; `User/APP/chassisL_task.c:38, 52-65, 130-133`). Confirm scheduling and motor-bus effects on hardware.
- Existing USART1 IRQ is priority 5 and its callback calls FreeRTOS `xQueueSendFromISR` (`Core/Src/usart.c:115-117, 151-165`). New DMA/idle IRQ priority and any RTOS API use must obey the configured FreeRTOS syscall-priority rules. Control-task priorities are software task priorities and do not by themselves establish IRQ latency bounds.
- Current USART1 receives one byte per interrupt; adding DMA/idle reception must replace/coexist carefully with `HAL_UART_Receive_IT`, callback behavior, the shared queue, and current ASCII parser. HAL UART calls also transmit synchronously with `HAL_MAX_DELAY` under a mutex; INS emits UART debug text around 50 Hz (`User/APP/INS_task.c:155-174`; `User/APP/app_uart.c:260-271`). Sharing USART1 could introduce blocking/contention or break the legacy interface.
- `chassis_move` and related fields are shared across tasks (`User/APP/ps2_task.c:48-50`; `User/APP/chassisR_task.c:44-49`). Keep advisory state separate and publish a coherent read-only snapshot; do not add parser writes to shared motion/FSM fields.
- Protocol constants and stale timeout are proposal values pending owner ratification (`TERRAIN_ADVISORY_FIRMWARE_PROPOSAL.md:15-18, 106-114, 128-147`). CRC is not authentication. Pi↔MCU clock mapping is not qualified. Board connector routing, actual logic levels/grounding, baud waveform/error, H7 parser timing, stack headroom, DMA placement/cache coherency, and ISR latency effects are **UNKNOWN** in reviewed material.
- Review found FDCAN3 initialized but apparently unused and the advertised USART1 `J` command parsed but not wired to jump state; confirm intended product behavior with owner.

## 6. Minimal owner-approved integration and bench plan

1. Owner selects/routs a UART, confirms 3.3 V logic and common ground, freezes the advisory protocol/session policy, buffer overflow behavior, timeout, and diagnostic counters. If using USART1, explicitly resolve existing ASCII/telemetry compatibility.
2. Add bounded DMA/ring reception and a low-priority decoder task; publish only an immutable snapshot. Leave all control, FSM, and actuator sources unchanged in telemetry-only phase. Build/map review should report H7 flash/RAM/stack and measure parser WCET and control-loop jitter.
3. On the real board with robot mechanically supported and **motors unpowered**, validate RX/TX pin continuity and idle voltage, then verify 460800 8N1 with a logic analyzer. Confirm delimiter/frame counts and MCU-local receive timestamps at 15 Hz.
4. Exercise good frames and COBS/CRC errors, wrong version/type/length, invalid enum/boolean/NaN/Inf, duplicate/old sequence/session, ring overflow, UART error, sender pause for 100/150/300/400 ms, and recovery. Check rejects do not refresh freshness; measure the stale transition from MCU time. Compare counters/decoded fields against known sender frames.
5. Observe ISR duration, decoder worst-case time, task stack watermark, queue/ring overflow, and balance-task timing under sustained traffic. Confirm all advisory values—including `JUMP_CANDIDATE`—remain telemetry only and there are no FDCAN motor commands caused by the input. Keep motors unpowered throughout.
